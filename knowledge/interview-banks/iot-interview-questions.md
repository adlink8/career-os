# IoT 方向面试题

> 针对 IoT 平台运维 / 设备接入岗位。结合用户 profile.yml 的项目经验。

## 一、MQTT 协议(必考)

### Q1:MQTT 的 QoS 等级有哪些?

- **答案要点:**
  - QoS 0:最多一次(发完不管,可能丢)
  - QoS 1:至少一次(可能重复)
  - QoS 2:恰好一次(开销最大)
- **追问:** "设备上报用哪个 QoS?" → 通常 QoS 1(平衡可靠性和开销)

### Q2:MQTT 的 keepalive 机制?(用户强项,必准备)

- **考点:** 用户的 AWS 项目就是排查 keepalive,这是**面试王牌**
- **答案要点:**
  - keepalive = 心跳间隔,客户端定期发 PINGREQ
  - 服务端预期时间内没收到 → 判定离线,发遗嘱消息(LWT)
  - keepalive 太短 → 频繁心跳耗流量;太长 → 离线检测延迟
- **用户案例衔接:**
  - 现象:设备频繁掉线
  - 排查:分析 MQTT 日志,发现 keepalive 间隔与网络实际往返不匹配
  - 解决:调整 keepalive 参数 + 优化重连逻辑
  - 成果:在线率 85% → 99%

### Q3:MQTT 和 HTTP 的区别?为什么 IoT 用 MQTT?

- **答案要点:**
  - MQTT 轻量(头部 2 字节 vs HTTP KB 级)
  - MQTT 长连接,HTTP 短连接
  - MQTT 发布订阅模型,适合一对多
  - MQTT 适合低带宽/高延迟/不稳定网络

## 二、设备接入

### Q4:海量设备接入怎么管理?

- **答案要点:**
  - 分级架构:网关 → 边缘 → 云
  - 设备分组 + Topic 设计
  - 连接池 + 限流
  - 时序数据库存储

### Q5:设备掉线如何检测和处理?

- **答案要点:**
  - keepalive 机制 + LWT 遗嘱消息
  - 心跳超时 → 标记离线 → 触发告警
  - 重连机制(指数退避)

## 三、AWS IoT(用户有项目)

### Q6:AWS IoT Core 的规则引擎作用?

- **答案要点:**
  - 对设备消息做过滤/转换/路由
  - 可以路由到 S3/DynamoDB/Lambda/Kinesis
  - 用 SQL 语法筛选
- **用户项目衔接:** "我在项目中用规则引擎把数据路由到 S3 存储"

### Q7:设备影子(Device Shadow)是什么?

- **答案要点:**
  - 设备状态的缓存(设备离线时也能读写状态)
  - reported(设备上报)+ desired(期望)两个状态
  - 用于离线控制 + 状态同步

## 四、数据管道(用户有基础)

### Q8:Kafka 在 IoT 数据流里的作用?

- **答案要点:**
  - 削峰填谷(海量设备突发数据)
  - 解耦(生产者/消费者分离)
  - 多消费者(数据同时进存储 + 实时分析)
- **用户衔接:** profile.yml 提到 Flume + Kafka + Flink 实践

## 五、故障场景

### Q9:设备数据丢失怎么排查?

- **答案要点(端到端排查):**
  1. 设备端:确认是否真的发送(MQTT 日志)
  2. 网络层:抓包确认数据出去
  3. 网关:确认收到并转发
  4. 云端:规则引擎是否匹配
  5. 存储:写入是否成功

### Q10:如何保证设备消息不丢?

- **答案要点:**
  - QoS 1/2 保证传输
  - 设备端本地缓存 + 重传
  - 云端幂等处理(防重复)
