# LC56 合并区间（中等·试水）

> ⚠️ 这题属于试水加餐：easy 全部通关后才做，卡住超时可看解析不丢人。
>
> 一句话考点：先把区间按起点排好队，再一趟扫过去"能接就接、接不上就另起一段" | 模式：排序 + 一趟合并

## 题面

以数组 `intervals` 表示若干个区间的集合，其中单个区间为 `intervals[i] = [starti, endi]`。请你合并所有重叠的区间，并返回一个不重叠的区间数组，该数组需恰好覆盖输入中的所有区间。

```text
示例 1：intervals = [[1,3],[2,6],[8,10],[15,18]] → [[1,6],[8,10],[15,18]]
        （[1,3] 和 [2,6] 重叠，合并为 [1,6]）
示例 2：intervals = [[1,4],[4,5]]                → [[1,5]]
        （端点相同也算重叠）
示例 3：intervals = [[1,4],[0,4]]                → [[0,4]]
```

约束：`1 <= intervals.length <= 10^4`，`intervals[i].length == 2`，`0 <= starti <= endi <= 10^4`。

```python
class Solution:
    def merge(self, intervals: list[list[int]]) -> list[list[int]]:
```

<details><summary>💡 提示第 1 档·方向（点开前先自己想 3 分钟）</summary>

想象一堆写着"起-止"的便签散在桌上，要找出能拼在一起的部分。散乱着拼很痛苦，但如果你先按便签上的**起点**从小到大排成一排，再从左往右看：当前便签的起点，是不是落进了前面正在拼的那一段的范围内？落进去就能拼（止点还要取更远的那个），落不进去就说明前一段彻底结束，另起一段。
</details>

<details><summary>💡 提示第 2 档·模式点名</summary>

排序 + 一趟合并。排序只做一件事：保证"可能重叠的区间一定挨在一起出现"，之后一遍线性扫描就能把所有重叠处理完。这是"先排序化乱为序、再线性处理"的通用套路，比逐对比较省一个数量级。
</details>

<details><summary>💡 提示第 3 档·步骤点破（卡死 15 分钟才许开）</summary>

1. 把 intervals 按每段的起点从小到大排序（这一步是一切的前提）；
2. 建一个结果列表，先把排序后的第一段放进去；
3. 从第二段开始逐个走：看它的起点是否小于等于结果列表**最后一段**的终点——小于等于，说明重叠，把最后一段的终点更新为"两者终点里更大的那个"；否则不重叠，把当前段整个放进结果；
4. 走完返回结果列表。
</details>

<details><summary>📝 三句口述参考</summary>

1. 遍历什么：排序后的 intervals，从第二段开始一趟走完。
2. 记录什么：结果列表 result，不断用新信息修正它的最后一段。
3. 怎么判断/返回：当前段起点 <= result 末段的终点 → 合并（终点取 max）；否则 result 追加新段。走完返回 result。
</details>

<details><summary>🔍 参考实现 + 逐行解析</summary>

```python
class Solution:
    def merge(self, intervals: list[list[int]]) -> list[list[int]]:
        intervals.sort(key=lambda x: x[0])
        result = [intervals[0]]
        for i in range(1, len(intervals)):
            if intervals[i][0] <= result[-1][1]:
                result[-1][1] = max(result[-1][1], intervals[i][1])
            else:
                result.append(intervals[i])
        return result
```

- 第 3 行 `intervals.sort(key=lambda x: x[0])` —— **按起点排队**，这题一切的前提。反过来会怎样：不排序，`[[1,4],[0,4]]` 走到第二段时它起点 0 没法和前面比，重叠的段擦肩而过，合并直接漏。`key=lambda x: x[0]` 意思是"按每段的第一格比大小"；只写 `sort()` 不带 key 也恰好按第一格排（列表逐格比），但显式写 key 更稳、意图更清楚。
- 第 4 行 `result = [intervals[0]]` —— 第一段先入住结果，后面循环从第二段开始。约束保证至少有 1 段，不用判空。
- 第 5 行 `for i in range(1, len(intervals)):` —— 从第二段（下标 1）开始逐个看。
- 第 6 行 `if intervals[i][0] <= result[-1][1]:` —— 重叠判断：当前段的起点，是否没越过结果里**最后一段**的终点。`result[-1]` 是结果列表的最后一个元素。为什么要看"最后一段"而不是更早的段？因为按起点排过队，更早的段要么已被并进最后一段，要么起点已确定不重叠——永远只需要盯最后一个。
- 第 7 行 `result[-1][1] = max(result[-1][1], intervals[i][1])` —— 合并：终点取两者**更大的那个**。反过来会怎样：写成直接 `= intervals[i][1]`，遇到 `[[1,10],[2,3]]` 会把末段终点从 10 错改成 3——新区间整体被包在旧区间里，终点反而变短了，后面所有判断全被带歪。
- 第 9 行 `result.append(intervals[i])` —— 不重叠：当前段另起一段入住。注意这里 append 的是原区间对象，后面若合并会原地改它——LeetCode 判题能过，但要明白 result 里的段是"活引用"不是拷贝。
- 第 10 行 `return result` —— 交卷。
</details>

<details><summary>🪤 常见坑（按杀伤力排序）</summary>

1. **忘记先排序**：现象——示例 3 这类"起点乱序"的用例错。病因：以为合并可以对着乱序输入直接做；排序是让"可能重叠的段挨在一起"的前提。修复：循环前先 sort。
2. **合并时终点直接覆盖**：现象——`[[1,10],[2,3]]` 类用例把终点改小。病因：默认新区间的终点一定更远，忘了"被包含"的情况。修复：终点取 `max(旧终点, 新终点)`。
3. **重叠判断写成 `<`**：现象——`[[1,4],[4,5]]` 返回两段，正确是一段。病因：题面明确"端点相同算重叠"（示例 2）。修复：判断用 `<=`。
4. **拿 intervals[i] 和 intervals[i-1] 比而不是和 result 末段比**：现象——连环重叠（三段以上叠在一起）漏合并。病因：合并后的段终点可能变长，原数组里前一个区间是"合并前"的旧终点。修复：永远和 result[-1] 比。
</details>

<details><summary>🎯 对账五问（做完再展开）</summary>

1. 第一个卡点通常在"没想到结构"——对乱序区间无从下手，没意识到"先排序"能一步把问题简化。
2. 最容易漏的动作：合并时终点取 max（而不是直接覆盖）。
3. 为什么这么解：暴力法每两个区间两两比较、合并后还要重头再来（合并可能引发连锁），最坏 O(n²)；排序 + 一趟是 O(n log n)——瓶颈全在排序上，扫描本身只 O(n)。为什么排序后一趟就够？因为按起点排队后，任何重叠的区间一定紧挨着出现，不需要回头。
4. 信号词："区间""重叠""合并"→ 排序 + 线性扫描；题面没说有序时，先排序几乎是条件反射。
5. 变式：插入一个新区间再合并（LC57）？排好序后同样的判断搬过来。判断一个人能否参加所有会议？把"合并"改成"发现重叠就返回 False"。
</details>
