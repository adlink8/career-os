# LC704 二分查找（简单）

> 一句话考点：翻字典猜页码，每次砍掉一半 | 模式：二分查找

## 题面

给定一个 `n` 个元素**有序**的（升序）整型数组 `nums` 和一个目标值 `target`，写一个函数搜索 `nums` 中的 `target`，如果目标值存在返回下标，否则返回 `-1`。

```text
示例 1：nums = [-1,0,3,5,9,12], target = 9  → 输出 4（9 在数组中，下标为 4）
示例 2：nums = [-1,0,3,5,9,12], target = 2  → 输出 -1（2 不存在，返回 -1）
```

约束：`1 <= nums.length <= 10^4`，`-10^4 < nums[i], target < 10^4`，nums 中所有值**互不相同**，数组**升序排列**。

```python
class Solution:
    def search(self, nums: list[int], target: int) -> int:
```

<details><summary>💡 提示第 1 档·方向（点开前先自己想 3 分钟）</summary>

翻一本厚字典找一个词，你会翻到正中间看一眼——目标在中间字的**前面还是后面**？翻错的那一半你**整本跳过**，再也不看。数组是有序的，这个"看中间、砍一半"的动作在数组上怎么做？什么条件下你敢断言"目标绝不在那一半里"？
</details>

<details><summary>💡 提示第 2 档·模式点名</summary>

二分查找：两个下标 left 和 right 圈出"目标可能在的范围"，每轮看正中间的 mid——比较后把范围砍一半。核心四件套：left 初值、right 初值、循环条件、left/right 怎么挪。四件套要互相咬合，改一个另外三个都得跟着改。
</details>

<details><summary>💡 提示第 3 档·步骤点破（卡死 15 分钟才许开）</summary>

1. left 站 0，right 站最后一格，两人之间是"嫌疑范围"；
2. 只要范围没消失（left 没越过 right）就继续找；
3. 每轮算出正中间的下标 mid；
4. mid 位置的数正好等于目标——交卷，返回 mid；
5. mid 的数比目标小——目标只可能在右半边，left 挪到 mid 后一格（mid 本身已排除）；
6. mid 的数比目标大——目标只可能在左半边，right 挪到 mid 前一格；
7. 循环走完范围缩没了还没找到，交卷返回 -1；
8. 死循环防线：mid 的取整方向和 left/right 的挪法必须配套，保证范围每轮**必定缩小**。
</details>

<details><summary>📝 三句口述参考</summary>

1. 遍历什么：不逐个遍历，只反复看"嫌疑范围"的正中间那个数。
2. 记录什么：left 和 right 圈住的范围，用 mid 取中间。
3. 怎么判断/返回：mid 命中返回 mid；mid 偏小砍左半（left = mid + 1），mid 偏大砍右半（right = mid - 1）；范围空了返回 -1。
</details>

<details><summary>🔍 参考实现 + 逐行解析</summary>

```python
class Solution:
    def search(self, nums: list[int], target: int) -> int:
        left, right = 0, len(nums) - 1
        while left <= right:
            mid = (left + right) // 2
            if nums[mid] == target:
                return mid
            elif nums[mid] < target:
                left = mid + 1
            else:
                right = mid - 1
        return -1
```

- 第 3 行 `left, right = 0, len(nums) - 1` —— 嫌疑范围是**闭区间** `[left, right]`：两头都算在内。right 取 `len(nums) - 1` 是因为下标从 0 数。这套初值和第 4 行的 `<=` 是一套的，改一个就要整套改（见坑 3）。
- 第 4 行 `while left <= right:` —— 闭区间的"范围还在"的写法：left == right 时范围里还剩**一个**候选，必须进去查，所以是 `<=` 不是 `<`。写成 `<` 的话，目标恰好在最后剩下的那一个位置时会漏查、误报 -1。
- 第 5 行 `mid = (left + right) // 2` —— 取范围正中间：相加除 2 向下取整。`//` 是整数除法，写 `/` 会得到小数当下标直接报错。Python 整数不会溢出，这个写法放心用（C/Java 里才有 `(left+right)` 溢出问题，届时用 `left + (right-left)//2`）。
- 第 6-7 行 `if nums[mid] == target: return mid` —— 正中目标，当场交卷返回下标。二分不是找完才返回，是**命中即走**。
- 第 8-9 行 `elif nums[mid] < target: left = mid + 1` —— mid 的数偏小，目标只能在右半边。**必须是 mid + 1 不是 mid**：mid 本身已经比过、不是目标，把范围砍到它身后。反过来会怎样：写成 `left = mid`，当范围缩到两个数、mid 算出来偏左时，left 不动，范围永远不变——**死循环**。
- 第 10-11 行 `else: right = mid - 1` —— 对称地，mid 偏大砍到它前面。同样必须 ±1，理由同上。
- 第 12 行 `return -1` —— 在 while **外面**：能走到这儿说明 left 已经越过 right、嫌疑范围缩没了还没命中，才有资格下"不存在"的结论。缩进写错进循环里的话第一个 mid 不中就交 -1。
</details>

<details><summary>🪤 常见坑（按杀伤力排序）</summary>

1. **`left = mid` 不挪动导致死循环**：现象——程序卡死（范围两个数时反复横跳）。病因：mid 已排除却还留在嫌疑范围里，范围不再缩小。修复：确认排除 mid 的写法就 ±1 到底——`left = mid + 1`、`right = mid - 1`，和 `while left <= right` 咬合。
2. **`//` 写成 `/`**：现象——`TypeError: list indices must be integers`。病因：`/` 出小数，下标必须是整数。修复：`mid = (left + right) // 2`。
3. **四件套不配套**：现象——漏查最后一个候选（初值 `len(nums)-1` 配了 `while <`）或越界（初值 `len(nums)` 配 `<=`）。病因：二分没有"万能写法"，初值、循环条件、±1 三者必须同一套约定。修复：先把"闭区间 + `<=` + ±1"这一套背成本能，别的变体（左闭右开）以后再学。
4. **比较方向写反**：现象——目标明明在右侧却返回 -1。病因：`nums[mid] < target` 理解成"mid 小所以往左找"。修复：背口诀"mid 偏小去右边"——数组升序，mid 的数比目标小，目标只能在它右边。
</details>

<details><summary>🎯 对账五问（做完再展开）</summary>

1. 第一个卡点通常在"±1 和循环条件怎么咬合"——这不是想出来的，是手推 `[5]`、`[5,7]`、`[5,7,9]` 各找一遍逼出来的。每个二分题都值得手推小数组。
2. 最容易漏的动作：挪边界时的 **±1**（排 mid）以及循环外的兜底 `return -1`。
3. 为什么快：暴力逐个翻页找是 O(n)——一万个数最坏看一万次；二分是 O(log n)——每看一次砍掉一半，一万次砍 14 刀就缩到 1。直觉：翻字典猜页码，错的那一半整本跳过，100 万个数也只需约 20 步。前提是数组**有序**——没有序就砍不动，这就是二分的入场券。
4. 信号词："有序""升序/降序""排序数组中查找"→ 二分。题面出现"有序"基本等于把二分写你脸上了。
5. 变式：找第一个等于 target 的位置？（LC35 的形，见下一题。）找比 target 小的最大数？（同套骨架，比较方向翻过来。）旋转有序数组找数（LC33，二分+判断哪半有序，medium 预告）。
</details>
